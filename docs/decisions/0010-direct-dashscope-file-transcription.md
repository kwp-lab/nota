# ADR 0010: Connect Directly to DashScope From the Nota Client

- Status: Accepted
- Date: 2026-08-22
- Last updated: 2026-08-22
- Decision owners: Nota maintainers

## Context

Nota users may choose Alibaba Cloud DashScope for whole-meeting transcription
with punctuation and anonymous speaker diarization. The recording and provider
API key already belong to the desktop application. Nota ASR Server is a
self-hosted inference service whose product boundary keeps customer audio in
an operator-controlled deployment; turning it into a cloud-provider proxy
would add a second upload hop, centralized vendor credentials, and unrelated
outbound-service lifecycle state.

DashScope file transcription requires a temporary upload, asynchronous task
submission, durable task-id polling, prompt result download, and provider-
specific normalization. DashScope temporary uploads are model- and account-
bound, expire after about 48 hours, and cannot be explicitly deleted. Its task
submission API does not provide Nota's idempotency key semantics.

Nota voiceprint analysis is an independent, optional FunASR Server workflow.
The product does not support running that workflow against a transcript whose
speaker partition was generated by DashScope.

## Decision

The Nota Rust backend connects directly to DashScope through a dedicated
provider adapter. React never performs provider HTTP or handles credentials or
recording bytes. Nota ASR Server remains unchanged.

The first version fixes the China public API endpoint and
`qwen-audio-3.0-asr-flash-filetrans`, uploads the original Ogg through
DashScope temporary storage, always enables diarization, and rejects recordings
longer than two hours before network access.

Provider capabilities and provider kind are snapshotted per transcription
generation. DashScope generations support manual meeting-local speaker naming
but never support Nota voiceprint analysis or enrollment. This rule does not
change when the user later selects another default provider.

The client persists upload and task checkpoints. It never automatically
resubmits an ambiguous task submission and never reports a running cloud task
as cancelled when the provider cannot cancel it.

## Alternatives Considered

### Proxy DashScope through Nota ASR Server

Rejected because it requires users to deploy an unnecessary intermediate
service, uploads the recording twice, expands the self-hosted server's trust
boundary, and duplicates provider configuration and task state.

### Treat DashScope as OpenAI-compatible chunk transcription

Rejected because independent chunks lose meeting-wide speaker scope and do not
match DashScope's asynchronous file-transcription protocol.

### Allow voiceprint analysis through a separately configured FunASR Server

Rejected for this release so that biometric feature availability remains an
explicit property of the transcription generation and the product does not
mix provider speaker partitions with a second provider's analysis.

### Require user-managed OSS in the first release

Rejected for the personal-project workflow. The adapter keeps upload behind a
boundary so a stable OSS strategy can be added later without changing task and
normalization behavior.

## Consequences

Positive:

- DashScope works without Nota ASR Server;
- the original Ogg uploads only once;
- users retain local provider selection and transcript storage;
- punctuation and speaker labels normalize into existing Nota transcript
  types;
- provider-specific feature limitations are visible and generation-stable.

Costs:

- the desktop owns a provider-specific asynchronous state machine;
- temporary uploads cannot be deleted immediately;
- running tasks cannot be remotely cancelled;
- an ambiguous submission requires explicit user action to risk resubmission;
- the fixed two-hour limit is stricter than the model's non-diarized maximum.

## Compatibility and Evolution

Existing FunASR and OpenAI-compatible protocols remain unchanged. New cloud
models that share DashScope only reuse this adapter when their request,
capability, and result contracts are explicitly verified. User-managed OSS,
workspace-specific endpoints, word-level UI, hotwords, context, other regions,
and voiceprint support require separate decisions rather than silent changes
to this first protocol.
